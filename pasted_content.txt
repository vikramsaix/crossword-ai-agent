### What I would build

Use **Python + an LLM through Token Factory**, with a solver architecture like this:

```text
Crossword Input
     ↓
Puzzle Parser
     ↓
Grid + Across/Down Constraint Model
     ↓
Candidate Generator (LLM)
     ↓
Candidate Scoring
     ↓
Constraint Solver / Backtracking
     ↓
Confidence + Conflict Resolution
     ↓
Completed Crossword
```

The important part is the **constraint-solving layer**. Suppose:

```text
1 Across: "Capital of France" (5)
Candidate → PARIS

2 Down: "A fruit" (5)
Candidates → APPLE, GRAPE, MANGO
```

Your program shouldn't independently accept whatever the LLM says. Every Across/Down answer shares letters with other answers. Those intersections become hard constraints.

For each clue, ask the model for perhaps **5–10 candidate answers with confidence/reasoning**, then rank candidates using clue relevance, required length, known crossing letters, and optionally model confidence. As more answers become known, re-query or re-rank uncertain clues. If you hit a contradiction, use **backtracking** rather than blindly continuing.

| Puzzle completion | % fully solved puzzles |
| Invalid crossings | Constraint failures |
| Runtime | Speed per puzzle |
| LLM calls | Efficiency |

**Baseline A:** one-shot LLM  
**Baseline B:** LLM + crossing constraints

### What they'll probably challenge you on

Be ready to explain **why an agent is needed**, why you didn't simply ask an LLM to solve the entire puzzle, how you deal with hallucinations, why you chose your candidate count, how confidence works, what happens when an early answer is wrong, how you prevent infinite backtracking, how you benchmarked it, what the largest failure category was, and what you'd improve with another week.

One particularly good design decision is to distinguish **LLM uncertainty from constraint certainty**. Crossing letters and answer lengths are deterministic; semantic clue interpretation isn't. Therefore your solver should allow the deterministic layer to overrule a confident but inconsistent LLM answer.

### Suggested implementation sequence

1. Define a clean JSON puzzle format and grid representation.
2. Extract Across/Down entries and their intersections.
3. Implement deterministic constraint checking **without any LLM**.
4. Build the Token Factory model adapter.
5. Generate structured candidate answers for each clue.
6. Implement candidate ranking.
7. Implement most-constrained-first solving + backtracking.
8. Add confidence/conflict handling.
9. Create unit tests.
10. Build the benchmark runner.
11. Compare against simpler baselines.
12. Add a lightweight UI/demo.
13. Write an excellent README with architecture, setup, evaluation and limitations.
14. Record the <1-minute demo only after your benchmark numbers are final.

The key is **don't over-engineer it into a huge multi-agent framework**. A well-engineered hybrid of **LLM candidate generation + classical constraint satisfaction + measurable evaluation** is easier to defend technically and demonstrates that you understand where AI should and shouldn't be used.
